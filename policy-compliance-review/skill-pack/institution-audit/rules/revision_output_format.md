# 修订清单输出格式规范（revision_output_format）

本规范定义"必须改"条款的最终交付格式，供修订技能（后续按条款定位逐条修订）直接消费。

> 版本说明：2026-08-27 按用户要求改版——**【修改】改为"问题+怎么办"**（不带条款定位、不带"类型X"编号），**【修订依据】改为"人话转述"**（不抄条文原文），批注文本三段用**真换行**分隔、**不含 article_id**。原文引用仅保留在《审核结果清单.md》（给审核确认用）。

## 1. 基本单位：一条清单 = 一个可定位的规范表述

- 每条清单必须能唯一定位到制度原文中的**一个具体位置**：条款（第X条），必要时精确到**款/项**（第X条第（Y）项）。
- **禁止合并**：同一"条"内多个独立问题（不同项、不同规范命题）必须拆分为多条清单，每条独立成文，不得合并为一条笼统意见。
- 拆分粒度示例：第八条第（十三）项与第八条第（十四）项各自独立成条，分别给出依据和建议。
- 若多个问题共享同一依据，允许重复引用，不得因"依据相同"而合并问题。
- 定位信息由**清单章节标题**（`## 1. 第三条`）和 **docx 批注锚点（commentRange）** 承担，【修改】字段本身不写位置。

## 2. 修改标题格式（问题 + 怎么办）

```text
【<修订性质>】<一句话问题概括>，<应如何处理>
```

- **标签随修订性质变化**：【修改】/【新增】/【删除】与 2b 节 `revision_type` 保持一致（新增性质写【新增】，删除性质写【删除】，替换写【修改】）。
- 不写条款位置、不带"类型X"编号（位置由批注锚点/清单标题承担）。
- 问题概括须为结论性表述；后半句给出处理方向（"应……"）。
- 示例：
  - `引用过时/错误依据，招标代理机构资格认定已取消，应修改该表述`
  - `未按法定指定媒介发布公告，应改按法定指定媒介发布并同步电子平台`
  - `履约保证金超过法定上限，应改为不得超过中标合同金额10%`

## 2b. 修订性质（必填，2026-08-27 17:54 定稿）

每条清单必须标注**修订性质**，取值三选一：`修改` / `新增` / `删除`。

```text
【修订性质】修改
{原始}：<最小修订范围的完整原文表述>
{修改}：<最小修订范围的完整修改后表述>
```

- **修改**（替换）：`{原始}` 放最小修订范围内**完整的原文表述**，`{修改}` 放**完整的修改后表述**；范围外的保留部分不写入。
- **新增**：`{新增}` 放新增内容。
- **删除**：`{删除}` 放被删除内容的完整原文表述。
- 判定原则：以**最小修订单元**为准——能局部替换的不得整句替换；只删不补=删除；只增不删=新增；删+补组合=修改。
- 数据字段：revision_list.json 每项含 `revision_type`、`min_original`、`min_modified`；`build_revision_list.py` **始终渲染该块**——`revision_type` 缺失时按 old/new（或 min 字段）自动推断并写回 json，min 字段缺失且有 old/new 时自动计算最小差异（无 old/new 时仅输出性质枚举，不输出键值行）。

## 3. 修订依据格式（人话转述）

```text
【修订依据】<先一句话概括"应如何做">。依据《法规名称》第X条（和第Y条）：<核心要义转述一两句>，<目的/后果>。
```

要求（用户 2026-08-27 18:10 定稿，范本思路——范本原文："租赁物应详细描述产权证号、配套设施及装修情况，并明确交付安全保障条款。依据《民法典》第七百三十一条，出租人应保证租赁物安全，承租人应有权因安全隐患解除合约，避免后续纠纷。"）：

- **整段成文、一段式**：先说正确做法（应如何做）→ 依据《法规》第X条转述核心要义 → 点明目的/后果。**禁止编号罗列法条**（"1. 依据… 2. 依据…"是反面典型）。
- **不整段抄条文原文**；用通俗语言转述（如"出租人应保证租赁物安全"而非"出租人应当按照约定将租赁物交付承租人，并在租赁期限内保持租赁物符合约定的用途"）。
- 多条依据合并进同一句："依据《A》第X条和《B》第Y条，……"。
- 每条依据必须含：法规全称（首次出现）或约定简称、条号；本地库可追溯的依据在修订清单.md 中保留 `（article_id=XXXX）`（批注中去掉）。
- 涉及废止/新法背景的，一句话带过并标注"（已废止）"，现行有效依据优先。
- 依据必须是本地 `law.db` 实际检索到的现行有效条文；已废止法规不得作为依据，仅可作背景说明。
- **本地库未收录但确属必要的依据**，必须如实标注 `（本地库未收录，待补录）`，不得假装在库。

## 4. 修订建议格式

```text
【修订建议】<可直接落地的修改文本>
```

要求：

- 给出**可直接替换/插入制度的成文表述**（"修改为：……"），而非泛泛方向。
- 需要删除的原文表述，用 `删除"……"` 明确列出。
- 如涉及多处修改，按（一）（二）（三）分点，每点对应一个可定位位置。

## 5. 数据字段（revision_list.json）

每条清单在 `revision_list.json` 中对应一个对象，除结构化字段外，**审核员必须逐条撰写两个展示字段**（人话版，供清单 md 与批注消费）：

| 字段 | 内容 | 用途 |
|---|---|---|
| `headline` | 人话版【修改】标题（问题+怎么办，不带位置） | 修订清单.md、【修改】 |
| `basis_human` | 人话版【修订依据】（法规名+条号+要义转述，**含 article_id**） | 修订清单.md、【修订依据】 |
| `suggestion` | 可执行修改文本 | 【修订建议】 |
| `revision_type` | 修订性质：修改/新增/删除 | 【修订性质】 |
| `min_original` | 最小修订范围的完整原文表述 | 【修订性质】{原始} |
| `min_modified` | 最小修订范围的完整修改后表述（新增时=新增内容） | 【修订性质】{修改}/{新增} |

`scripts/build_revision_list.py` 优先输出 headline/basis_human；缺省回退 `error_type` + 原文 basis（仅当未撰写时）。

## 6. 依据核验说明

清单末尾附"依据核验说明"表（按 article_id 去重）：

| 依据 | 本地库状态 |
|---|---|
| 法规名（article_id） | ✅ 已入库 |
| 法规名 | ❌ 待补录 |

## 7. 与审核结果字段的映射

`audit_results.json` 中每条 `必须改` 记录与清单的映射：

- `clause_id` / `clause_label` → 清单章节标题
- `headline` → 【修改】；`basis_human` → 【修订依据】；`suggestion` → 【修订建议】
- `basis[]`（law_name/article_no/content）→ 核验表与追溯

拆条后，同一 clause_id 允许多条清单（用 `clause_id + 项号` 区分，如 `C08-13`、`C08-14`）。

## 8. 批注文本消费规则（doc-revision-annotate 衔接）

生成修订批注版 docx 时，批注文本由 `revision_list.json` 生成，**四段式**（2026-08-27 17:57 定稿）：

1. **四段用真换行分隔**：`【修改】…\n【修订依据】…\n【修订建议】…\n【修订性质】…`（脚本自动转 w:br；禁止用 `｜` 或空格分隔）
2. **去掉 article_id**：`（article_id=XXXX）` 一律从批注文本中清除（保留法规名+条号即可，可追溯性由修订清单.md 承担）
3. **【修订性质】末段为结构化信息（供前端解析展示，非阅读用途）**，格式：
   - 修改：`修改` + `{原始}：<min_original>` + `{修改}：<min_modified>`（每行一个键值）
   - 新增：`新增` + `{新增}：<内容>`
   - 删除：`删除` + `{删除}：<内容>`
   - 旧数据无 `revision_type` 时回退 `修改` 且不输出 {原始}/{修改} 行
4. **首段标签随修订性质变化**：【修改】/【新增】/【删除】与 revision_type 一致

生成命令（固化脚本）：

```bash
python3 scripts/build_comment_items.py --revision <revision_list.json> --items <items.json>
```

- 按 `clause_id`（或 `clause` 文本前缀匹配 clause_label）逐条填 comment 四段式
- 默认清理 article_id（`--keep-aid` 可保留）；清理时注意空括号残留（见坑 ②）

## 9. 交付场景

- 用户要求"审核结果清单/修改清单"时，按本格式输出。
- 修订技能按条款定位消费清单时，以 `clause_id + 项号` 为定位键，不得跨条合并。
- 修订批注版 docx 的批注文本必须与此处【修改】/【修订依据】/【修订建议】一致（由 build_comment_items.py 保证）。
- **批注逐条、不合并（2026-09-01 用户明确）**：修订清单怎么给，批注就怎么给——每个清单条目对应一条独立批注，精确锚定该条目自己的修订处；同一"条"下多个子项（如第八条第（六）（九）（十三）项）各自独立成批注，**禁止**合并为一条笼统批注，也**禁止**把整条条款整体做一条批注。revision_edit.py 默认逐条批注（仅 items.json 顶层显式 `"merge_by_clause": true` 时才按条款合并，需用户明确要求）。
