# 合同审核

> 客户为某化工集团，项目信息已脱敏处理。

## 项目背景

在商务同事协助下，基于非框架、框架和子合同模板梳理合同审核规则。

## 我的工作

- 梳理“固定条款完整性核对＋待填项逐项校验”规则，按客户业务反馈完成四轮修订。
- 独立配置智能体并测试 18 份样本材料，面向客户进行智能体效果演示。

## 成果

- 测试中识别出海外项目双语供需合同中英文交货时间约定冲突，获得客户认可。
- 获得将审核用于业务部门前置审核的反馈。

## 审核路径

技能的第一步不是读条款，而是先判立场、再判业态——不同立场和业态走完全不同的审核标准：

```text
① 立场判定：某集团是需方/买方（采购轨）还是供方/卖方（销售轨）
② 业态判定：集团标准模板 → 条款核对；非集团模板 → 采购 SOP 全面审查；销售合同 → 销售 SOP
③ 主体审核（签约主体履约能力、涉诉与失信查询）
④ 逐项审核（按所选轨道的检查表）
⑤ 双通道输出：Word 批注（仅高风险）+ 对话窗口完整结论
```

## 交付物说明

`skill-pack/` 是项目的核心交付物，包含技能入口 `SKILL.md`、三套分轨审核标准（集团模板条款核对、非模板采购 SOP、销售合同 SOP）、批注输出规范，以及工具脚本：docx 全文提取、内容控件精准批注、修订标记修改、印章检测、PaddleOCR 视觉识别。

其中比较硬的工程细节是 docx 解析。集团模板合同的填写值存放在 Word 内容控件（`w:sdt`）里，python-docx 的标准 API 读不到，曾把一份填写完整的合同误判为「首部全部空白」；修复后不久又出现整块被 `w:sdt` 包裹的段落（`sdtBlock`）被漏读，导致「条款跳号、缺 8–14 条」的误报。这两次事故都被固化成强制规则：解析前先统计 `w:sdt` 数量、改用 XML 级提取并递归展开 `sdtContent`、批注落版前做条款序列完整性校验。
