# 合同审核助手 · 技能包

> 客户为某化工集团，项目信息已脱敏处理。

这是 Claworks 平台上的合同审核技能，为某化工集团采购业务定制：在提交法务正式审核之前，对采购合同做一遍可复现的技术性初审，识别条款缺失、金额错误、合规红线和信息空白，并把结论落到原文锚点上。

## 审核路径：先判立场，再判业态

技能的第一步不是读条款，而是确定「我方是谁、这是哪类合同」，因为不同立场和业态要走完全不同的审核标准：

```text
合同文件
  ↓
① 立场判定：某集团是需方/买方（采购轨）还是供方/卖方（销售轨）
  ↓
② 业态判定
    ├─ 采购轨 + 集团标准模板（含框架主合同、子合同、跟单）→ 轨道A：条款核对
    ├─ 采购轨 + 非集团模板                                        → 轨道B：采购合同审核 SOP 全面审查
    └─ 销售轨                                                     → 供应商销售合同审批 SOP
  ↓
③ 主体审核（签约主体履约能力、涉诉与失信查询）
  ↓
④ 逐项审核（按所选轨道的检查表）
  ↓
⑤ 双通道输出：Word 批注（仅高风险）+ 对话窗口完整结论
```

集团内部关联购销、立场无法判断等情况强制要求向用户确认，不允许猜。

## 三套审核标准

| 文件 | 适用场景 | 审核重点 |
| --- | --- | --- |
| `references/集团格式合同审核-条款核对.md` | 集团标准模板合同（框架主合同／子合同／非框架） | 防删减、漏填、弱化。含三类模板的待填项全量清单：普通合同 46 项、框架合同约 73 项、子合同 34 项；子合同必须回溯核验框架主合同生效状态 |
| `references/采购合同审核SOP.md` | 非集团模板的采购合同 | 逐条全面审查，含保护性条款清单与合规红线一票否决项 |
| `references/供应商销售合同审批sop.md` | 我方为供方/卖方的销售合同 | 按甲方立场与乙方立场分别列出审核要点 |

三套标准都维护了「调整记录总表」，把每次客户反馈落到具体条款，保证规则是可追溯、可版本化的，而不是散落在提示词里。

## 关键设计

### 解析事故固化成规则：docx 内容控件与块级控件

这是这个技能里最硬的一段经验。集团模板合同的填写值大量存放在 Word 内容控件（`w:sdt`）里，而 python-docx 的标准 API 读不到——曾经把一份填写完整的合同误判为「首部全部空白」。修复后写进了强制规则：

- 解析前先统计 `w:sdt` 数量，大于 0 一律改用 XML 级提取工具 `scripts/xml_extract.py`，禁止用 python-docx API 直接下审核结论
- 随即出现第二次事故：整块被顶层 `w:sdt` 包裹的段落（`sdtBlock`）被漏读，导致「条款跳号、缺 8–14 条、全文无争议解决条款」的误报。修复版递归展开 `sdtContent`
- 批注落版前增加强制完整性校验：条款标题序列与已知模板结构交叉验证，缺条即视为提取异常；存疑时用 `w:t` 全文直查复核，禁止直接判定「条款缺失」

### 双通道输出，批注只标高风险

- **通道一（Word 批注）**：只标高风险问题——合同效力、金额错误、合规红线、重大利益损失、主体异常、影响结算/验收/生效的信息空白。批注不显示级别只显示类别（金额异常／签署缺失／付款风险／质保期等），正文固定为「【类别】一句话概括 → 问题与风险（引用原文）→【修改建议】→【依据】」，署名「合同审核助手」，禁用 emoji（WPS 不兼容）
- **通道二（对话窗口）**：完整结论，含中低风险项与谈判要点
- **锚点规则**：每个问题一条批注；空白项锚定在空白填写处本身，不锚表头；同段多问题拆多条；锚定匹配只允许在单段／单单元格内进行，禁止跨段拼接（这也是实战踩出来的）

### 扫描件（PDF/图片）的处理策略

- 用 PaddleOCR-VL 做视觉识别，输出 Markdown 与版面坐标；本地 tesseract 作兜底
- 印章检测单独成工具 `scripts/check_seal.py`，用颜色与形状分析识别红/蓝/深色印章并给出签章区分析，同时明确它是辅助手段、仍须纸质核验
- 批注交付按风险分级控制成本：中低风险用图钉便签（`add_text_annot`），高风险条款才用半透明矩形框选；表格类扫描件没有行级坐标，就用「条带 OCR 校准」——按 x 区间切横向条带二次 OCR，实测条款 y 区间，而不用比例模型粗估

### 主体履约能力查询

审核非政府机构签约主体时，强制调用统一搜索服务（涉诉、失信被执行、经营异常、行政处罚）。接口地址在仓库中已替换为占位符。

## 目录结构

```text
skill-pack/
├── SKILL.md                          # 技能入口：身份、流程、红线、资源索引
├── assets/templates/                 # 输出模板资源
├── references/
│   ├── 集团格式合同审核-条款核对.md    # 轨道A：集团模板条款核对
│   ├── 采购合同审核SOP.md             # 轨道B：非模板采购合同审查
│   ├── 供应商销售合同审批sop.md        # 销售轨
│   ├── 合同审核批注模板.md            # 批注输出规范（双通道、类别词表、锚点规则）
│   ├── 输出模板.md                   # 审核报告格式
│   └── 系统对接.md                   # 外部服务与工具链说明
└── scripts/
    ├── xml_extract.py                # docx 全文提取（XML 级，含 sdt）
    ├── add_comments_sdt.py           # 内容控件合同的精准批注
    ├── add_comments.py               # 普通 docx 批注
    ├── revision_edit.py              # 修订标记修改 + 批注
    ├── revision_edit_v2.py           # 修订工具 v2（甲方立场场景）
    ├── check_seal.py                 # 印章检测
    └── paddleocr_ocr.py              # PaddleOCR-VL 视觉识别
```

## 运行依赖

- Python 3.10+；`python-docx`、`docx-comments`、`lxml`、`requests`
- LibreOffice（doc ↔ docx 转换）
- PyMuPDF、pdftoppm（扫描件批注与坐标换算）
- PaddleOCR-VL API Token：通过环境变量 `PADDLEOCR_TOKEN` 或 `~/.paddleocr_token` 提供，脚本内不落盘、仓库中不含任何密钥

## 未包含的内容与脱敏说明

- 未纳入两个一次性调试脚本（`final_fix.py`、`fix_remaining.py`）：它们按段落索引硬编码针对某一份合同的修补动作，属于开发过程中的临时脚本，不构成可复用能力。
- 脱敏处理：客户名称与其子公司名称统一替换为「某化工集团」「某氟化工子公司」等；文档中的纪检举报电话与投诉邮箱替换为「（已隐去）」；内部服务地址（`10.x.x.x` 内网接口）替换为占位符；示例中的签约主体名称替换为「某设备公司」。
- 仓库中不包含任何客户合同原件或审核输出成果。
